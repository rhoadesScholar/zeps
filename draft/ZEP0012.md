# ZEP 12 — Explicit array bounds

Authors:

- [Jeff Rhoades](https://github.com/rhoadesScholar), E11 Bio

Status: Draft

Type: Specification

Created: 2026-10-19

Discussion: https://github.com/zarr-developers/zarr-extensions/issues/79

## Abstract

A Zarr v3 array occupies the coordinates `[0, shape)` along each dimension, and the regular chunk
grid is anchored at coordinate 0. Together these make growing an array before its first element the
one resize that cannot be done by editing metadata: every existing chunk has to move to a new key,
or be copied. This ZEP adds `bounds` to the array metadata as an alternative to `shape`, giving each
dimension an explicit half-open coordinate range, and an optional `origin` to the regular chunk
grid, giving the array coordinate at which chunk grid index 0 starts. Chunk grid indices may then
be negative. Adding `n` elements in front becomes a change to one number in `zarr.json`; existing
chunks keep their keys and existing elements keep their coordinates. Arrays written with `shape`
are unchanged, and a reader that does not implement this ZEP refuses an array that uses it.

## Motivation and Scope

Volumes that are assembled over time rarely arrive in index order. Serial-section imaging adds
sections at either end of a stack; a tiled acquisition is registered as tiles land, and the first
tile is not the one at the corner; a time series gets a backfill. In every case the existing data
should keep its coordinates, because other arrays, annotations and viewers already refer to them,
and the new data goes in front.

Zarr v3 cannot express that. Coordinates run from 0 and the regular chunk grid is aligned at 0, so
the only way to add `n` elements before the first is to grow `shape` and shift everything else by
`n`: every chunk is read and written under a new key (or renamed, on a filesystem), and every
coordinate held outside the array is off by `n`. The cost is proportional to the number of chunks,
and on an object store to the number of bytes, which is the opposite of what a resize should cost.
The regular grid specification anticipates the fix: it notes that "extensions may define variations
on the regular grid type such that the grid indices may include negative integers, and the origin
element of the array may occur at an arbitrary position within any chunk, which is required to
allow arrays to be extended by an arbitrary length in a 'negative' direction along any dimension."

A chunk grid extension can do it, and
[zarr-extensions#81](https://github.com/zarr-developers/zarr-extensions/pull/81) prototypes one,
but the discussion in
[zarr-extensions#79](https://github.com/zarr-developers/zarr-extensions/issues/79) converged on a
core change instead. A chunk grid's job is to map coordinates to chunks; where the coordinates
start is a property of the array. A metadata-only reader, one that reports the extent of an array
from `shape` and `data_type` without consulting the chunk grid, would silently report the wrong
extent if the lower bound lived inside `chunk_grid`. Putting the bounds where `shape` is means a
reader either understands them or refuses the array.

In scope:

- a `bounds` member of the array metadata, as an alternative to `shape`;
- an optional `origin` in the `regular` chunk grid configuration, and negative chunk grid indices;
- how the `default` and `v2` chunk key encodings write a negative index.

Out of scope: the rectilinear chunk grid, which is a registered extension and would gain the
matching fields in its own specification (see Implementation); dimensions of infinite or unknown
extent; how implementations expose array indices to their users.

## Usage and Impact

What users see is up to each implementation's array API. zarr-python's prototype keeps zero-based
indexing, so `a[0]` is the first element before and after a prepend, and reports the coordinate
range as a separate property:

```python
import numpy as np
import zarr

a = zarr.create_array(store, shape=(6, 4), chunks=(4, 2), dtype="int32")
a[:] = np.arange(24).reshape(6, 4)       # chunks c/0/0, c/0/1, c/1/0, c/1/1

a.prepend(np.full((3, 4), -1), axis=0)   # one zarr.json write, then the new chunks
a.shape    # (9, 4)
a.domain   # ((-3, 6), (0, 4))
a[3:]      # the original data; its chunks were not touched
```

The metadata after the prepend:

```json
{
  "bounds": [[-3, 6], [0, 4]],
  "chunk_grid": {"name": "regular", "configuration": {"chunk_shape": [4, 2]}}
}
```

The three new rows fill the rest of chunk `-1` along the first dimension, stored under `c/-1/0`
and `c/-1/1`. Nothing else in the store changes.

The same growth today, for an array on a filesystem store, is a `resize` followed by a move of
every chunk to its new key, highest index first so that no key is overwritten:

```python
a.resize((a.shape[0] + k * a.chunks[0],) + a.shape[1:])
for i in reversed(range(n0)):
    for j in range(n1):
        os.rename(root / "c" / str(i) / str(j), root / "c" / str(i + k) / str(j))
```

On an object store it is a copy and a delete per chunk, or a copy of the whole array. Measured on
one machine with 64³ `uint8` chunks (262 KiB each), growing by two chunk rows, the metadata step
against the three ways available today:

| chunks | rename (filesystem) | copy + delete per chunk | copy the array | metadata write |
|-------:|--------------------:|------------------------:|---------------:|---------------:|
|  4 096 |              0.13 s |                   5.9 s |          3.1 s |        0.002 s |
| 32 768 |               1.0 s |                    44 s |           26 s |        0.002 s |

The measurement used the chunk grid prototype of zarr-extensions#81; under this ZEP the metadata
step is the same single write of `zarr.json`. Writing the new data costs the same in every column
and is not included. The first three columns grow with the array; the last does not.

For a reader the change is a translation: coordinate `x` is in chunk `floor((x - origin) / d)`
instead of `floor(x / d)`, and the first chunk may be partial where only the last could be before.
tensorstore's prototype maps the lower bound onto its index domain and lets a resize move it;
neuroglancer's displays the array at its coordinates, as it does for its precomputed format's
`voxel_offset`.

## Backward Compatibility

Arrays written with `shape` are unaffected: their metadata is unchanged and means what it meant.

An array that uses `bounds` has no `shape`. `shape` is mandatory today and every implementation
checked refuses an array metadata document without it, so an implementation that does not know
this ZEP fails to open such an array rather than misreading it. That is why `bounds` replaces `shape` instead of sitting beside
it, and why `origin` is only permitted together with `bounds`. The alternatives were checked
against current readers, and some open the array and address every chunk from 0:

| metadata | zarr-python | tensorstore | neuroglancer |
|---|---|---|---|
| `origin` inside the `regular` configuration, with `shape` | opens, ignores it | refuses | opens, ignores it |
| an unknown top-level member next to `shape` | refuses | refuses | opens, ignores it |
| `shape` absent | refuses | refuses | refuses |

(zarr-python and neuroglancer from their main branches in October 2026, tensorstore 0.1.85.)

Any array converts between the two forms without touching a chunk: `bounds[i] = [0, shape[i]]`,
and back when every lower bound is 0. Writers SHOULD write `shape` whenever every lower bound and
every `origin` entry is 0, so that arrays which do not need this feature stay readable everywhere.

This is an additive change: a minor version of the core specification, with the regular chunk grid
and the `default` and `v2` chunk key encodings each moving to version 1.1.

## Detailed description

### `bounds`

An array metadata document MUST contain exactly one of `shape` and `bounds`.

`bounds` is an array with one entry per dimension. Each entry is a two-element array of integers
`[start, stop]` with `start <= stop`; the elements of the array along that dimension have the
coordinates `start, start + 1, ..., stop - 1`. A dimension with `start == stop` has length 0. A
zero-dimensional array has `"bounds": []`.

The shape of the array is derived: the length of dimension `i` is `stop_i - start_i`. `shape`
keeps its meaning and is equivalent to `bounds` with `start` 0 along every dimension. Wherever the
specification refers to the shape or to the length of a dimension, the derived value applies;
`dimension_names`, if present, has one entry per dimension.

### `origin` on the regular chunk grid

The `regular` chunk grid configuration gains an optional member `origin`: an array of integers with
one entry per dimension, the array coordinate at which chunk grid index 0 begins along that
dimension. `origin` MAY only be present when the array metadata uses `bounds`. When absent it is 0
along every dimension, which is the current grid.

Along a dimension with chunk length `d` and origin `o`, chunk grid index `g` covers the coordinates
`[o + g * d, o + (g + 1) * d)`. The element at coordinate `x` is in the chunk with grid index
`floor((x - o) / d)`, at position `(x - o) mod d` within it, with floor division and the modulo
that pairs with it so that both are defined for `x < o`. Grid indices MAY be negative.

Along a dimension with bounds `[start, stop)` the grid runs from grid index `floor((start - o) / d)`
through `floor((stop - 1 - o) / d)` when `stop > start`, and has no chunks otherwise. The first
chunk MAY contain positions below `start`, exactly as the last chunk may contain positions at or
above `stop`: those positions are not elements of the array, and a writer SHOULD store the fill
value there. Every chunk is encoded at the full `chunk_shape`.

With `origin` 0 the chunk holding the first element is `floor(start / d)`, and with `start` 0 it is
chunk 0, as today. The sharding codec is unaffected: its inner chunks are positioned relative to
the shard they are in.

### Growing and shrinking

To add `n` elements before the first along dimension `i`, a writer sets `bounds[i][0] -= n`.
`origin` and the grid index of every existing chunk are unchanged, so no chunk changes key and
every existing element keeps its coordinate. The new elements occupy the rest of what was the first
chunk and, when `n` is large enough, chunks at lower grid indices. Growing after the last element is
`bounds[i][1] += n`, as `shape[i] += n` is today, and shrinking from either end is the matching
decrease. The specification's note on resizing applies at both ends: chunks that already exist in
the region being grown into are shown unless the writer clears them.

`origin` also lets a writer translate an array's coordinates without moving chunks: adding `k` to
both entries of `bounds[i]` and to `origin[i]` leaves every chunk under the same key.

### Negative chunk indices in chunk keys

The `default` and `v2` chunk key encodings write each grid index as its ASCII decimal string; a
negative index carries a leading `-`, as in `c/-1/0`. The string `-0` MUST NOT be written and MUST
be rejected when a key is parsed. Negative components do not sort numerically under the
lexicographic order of keys (`c/-2` sorts after `c/-1`), which an implementation that lists keys by
range has to allow for.

### What implementations expose

This ZEP defines coordinates in the stored representation. Whether an implementation indexes by
coordinate, or keeps zero-based indices and reports the coordinate range separately, is its own
choice; zarr-python's prototype does the second, tensorstore does the first through its index
domain. A convention layered on Zarr that positions the first element, such as an OME-NGFF
`translation`, points at a different element after a prepend, so a writer updates it by the amount
grown; the existing elements do not move.

### Example

```json
{
  "zarr_format": 3,
  "node_type": "array",
  "bounds": [[-3, 6], [-2, 7]],
  "data_type": "uint16",
  "chunk_grid": {
    "name": "regular",
    "configuration": {"chunk_shape": [4, 5], "origin": [0, 0]}
  },
  "chunk_key_encoding": {"name": "default"},
  "codecs": [{"name": "bytes", "configuration": {"endian": "little"}}],
  "fill_value": 0
}
```

A 6 by 7 array with 4 by 5 chunks, grown by 3 rows and 2 columns in front. Its elements occupy
`[-3, 6) x [-2, 7)` and the grid indices run `-1, 0, 1` along both dimensions. The first element is
at position 1 of chunk `-1` along the first dimension and position 3 of chunk `-1` along the second.
The original four chunks keep their keys `c/0/0`, `c/0/1`, `c/1/0` and `c/1/1`; the new ones are
`c/-1/-1`, `c/-1/0`, `c/-1/1`, `c/0/-1` and `c/1/-1`.

## Related Work

- [tensorstore](https://google.github.io/tensorstore/) gives every array an index domain with an
  inclusive lower and exclusive upper bound per dimension, either of which may be implicit so that
  a resize can move it. The
  [neuroglancer precomputed format](https://github.com/google/neuroglancer/blob/master/src/datasource/precomputed/volume.md)
  stores a `voxel_offset` beside each scale's `size`. Both are coordinate ranges that need not start
  at 0, over a chunk grid whose alignment is independent of the lower bound.
- [Icechunk](https://icechunk.io/)'s `shift_array` moves chunk references by whole chunks inside its
  versioned store. It does not change the plain Zarr representation and works in chunk units.
- zarr-indexing, in the zarr-python repository, separates a zero-based positional dialect from an
  absolute index domain and works through negative-origin domains and prependable grids in its
  design notes.
- The [rectilinear chunk grid](https://github.com/zarr-developers/zarr-extensions/tree/main/chunk-grids/rectilinear),
  from ZEP 3, varies the chunk length along a dimension; it is the other grid that needs an origin
  to support negative indices.
- OME-NGFF defines its index space as zero-based from the first element, and places it with a
  `translation` per level.

## Implementation

Three prototypes exist, currently on the chunk grid form of this design (`regular_bounded` in
zarr-extensions#81, whose configuration carries `origin` and `lower_bound`). Each reads those two
fields in one place, so moving the lower bound to `bounds` is a small change in each:

- zarr-python [#4516](https://github.com/zarr-developers/zarr-python/pull/4516): `Array.prepend`
  and `Array.domain`; indexers offset by the first element's position in its chunk.
- tensorstore [#296](https://github.com/google/tensorstore/pull/296): bounds as the index domain,
  resizing of the lower bound, negative components in key range listing.
- neuroglancer [#1133](https://github.com/google/neuroglancer/pull/1133): read support, chunk space
  relative to `origin`.

Steps:

1. A zarr-specs pull request with the changes described here: core specification (`bounds`,
   derived shape, example, resizing note), regular chunk grid (`origin`, negative indices, partial
   first chunk), `default` and `v2` chunk key encodings (sign, `-0`).
2. Rework the three prototypes to read `bounds` and `origin`.
3. Propose `origin`, together with the grid index of the first listed chunk, for the rectilinear
   chunk grid in zarr-extensions.
4. On acceptance, withdraw zarr-extensions#81. If this ZEP is not accepted, that registry entry
   remains the fallback.

## Alternatives

- **A chunk grid extension** (zarr-extensions#81: `chunk_shape`, `origin`, `lower_bound` in the
  grid configuration). Needs no specification change, and every current reader refuses an unknown
  grid name, so it is safe. Not chosen because it puts the array's extent inside the chunk grid,
  where a reader that consults only `shape` reports the wrong one.
- **`lower_bound` as a new top-level member next to `shape`.** The smallest change to each reader.
  Not chosen because its safety rests on readers refusing unknown top-level members, which at least
  one widely used reader does not do.
- **An `offset` chunk key encoding** (zarr-extensions#80), shifting the key numbering by a stored
  offset. Withdrawn on review: tied to one encoding, worse key ordering, shifted logical
  coordinates, and no growth by part of a chunk.
- **Two members, `lower_bound` and `upper_bound`,** instead of per-dimension pairs. Equivalent;
  pairs keep a dimension's extent in one place and leave a single exactly-one rule against
  `shape`. Either would do.
- **Status quo:** rename or copy every chunk, or create the array with headroom in front. The first
  costs the whole array; the second is a guess.
- **A store-level shift,** as in Icechunk. Only in that store, and only by whole chunks.
